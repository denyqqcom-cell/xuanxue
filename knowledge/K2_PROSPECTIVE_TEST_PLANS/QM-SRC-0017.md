## Test A — SOURCE_FIXED_LOOKUP vs CONTEXT_FROZEN_RELATIONAL

Question:

Does the project's contextual-relational method provide measurable value beyond a simpler source-bound lookup/role model?

For future clean low-risk unknown-outcome cases, freeze before feedback:

### Model A1 — SOURCE_FIXED_LOOKUP

- fixed source/method family;
- fixed role/lookup rules eligible for the case type;
- one primary branch;
- explicit abstain condition;
- no broad symbolic expansion after the freeze.

### Model A2 — CONTEXT_FROZEN_RELATIONAL

- same source exposure baseline;
- actors / target / horizon / constraints frozen;
- Role Map frozen;
- eligible structural features frozen;
- finite relation chain;
- one primary branch or pre-weighted branches;
- explicit failure condition.

Primary comparisons:

- reproducibility across analysts/reruns;
- outcome discrimination;
- calibration;
- abstention quality;
- number of free choices before freeze;
- complexity cost.

Falsification condition for current context theory:

If A2 does not materially outperform A1, or only does so by using more eligible meanings/branches, the extra context machinery must be compressed.

## Test B — Context Compression vs Context Expansion

Question:

Does adding real-world context reduce legal interpretation space as intended, or merely increase narrative rescue capacity?

Pre-register three variants:

1. `MINIMAL_CONTEXT`: only neutral setup facts;
2. `FROZEN_CONTEXT`: relevant actors/target/horizon/constraints, but eligible meanings must narrow;
3. `BROAD_CONTEXT`: broader descriptive background while keeping outcome hidden.

Track:

`eligible_meaning_count / role_map_alternatives / branch_count / timing_alternatives`.

Expected theory behavior:

`FROZEN_CONTEXT` should reduce or hold degrees of freedom while improving discrimination.

Failure signal:

If broader context makes more branches/meanings admissible without improving prospective discrimination, flag `CONTEXT_EXPANSION / NARRATIVE_RESCUE_RISK` and narrow the protocol.

## Test C — Source-defined state classification ablation

Question:

Do star/gate state classifications add predictive discrimination beyond the same model without those states?

Variants:

- `STRUCTURE_ONLY`;
- `STRUCTURE_PLUS_SOURCE_STATE`;
- `SHUFFLED_STATE` negative control.

Rules:

- no invented numeric weights;
- source-defined state system must be frozen;
- applicability season/month object must be explicit;
- effect-size is measured from outcomes, not assigned from terminology.

Failure signal:

If `STRUCTURE_PLUS_SOURCE_STATE` does not outperform `STRUCTURE_ONLY`, or `SHUFFLED_STATE` performs similarly, demote the state layer.

## Test D — Fixed-bureau implementation witness

Question:

Can selected source tables be reproduced by an executable profile while rejecting deliberately wrong structures?

Procedure:

1. select a small non-substantial subset of visually verified table anchors;
2. transcribe expected values independently from implementation;
3. identify exact method/time-family object;
4. compare production output;
5. run wrong-bureau / permuted-star / permuted-door / shuffled-structure controls.

Credit boundary:

Pass increases `Implementation Fidelity` only.

It does not prove the table predicts reality.

## Test E — Time-family ontology separation

Question:

Are time-family methods representable as one shared engine with flags, or do they require separate object schemas?

For each family studied, freeze:

- star set;
- gate set;
- palace/rotation object;
- time input;
- setup rule;
- state objects;
- interpretation role vocabulary.

Compare object homology before code reuse.

Failure condition for a universal engine:

If two families share labels but require incompatible object sets or movement semantics, split the runtime model instead of adding ad-hoc exceptions.

## Test G — Simpler cross-family structural core

Candidate abstraction:

`OBJECT -> ROLE -> STATE -> RELATION -> DISCRIMINATING OUTCOME`

Question:

Can this minimal abstraction represent several explicitly different Qimen families without silently merging their ontologies?

Pass condition:

- each source object retains family identity;
- only genuinely homologous relations are shared;
- no source-specific token is redefined to fit the abstraction;
- the abstraction reduces implementation/interpretation complexity.

Failure condition:

If substantial ad-hoc mappings are needed, the abstraction is too broad and must split.
