# 闭关回看：内驱、周期与理论版本校准（2026-08-21）

状态：ACTIVE SELF-AUDIT / 不产生 Reading 或 Empirical Support credit

## 一、这轮回头看见的新风险

前面已经防过“把书当圣经”，但项目本身也可能重新长出新的圣经：固定流程、固定 sprint、固定队列、频繁理论版本号。

最危险的不是旧错误原样回来，而是换成更专业的外衣回来。

### 1. 时间盒可能从防拖延变成被动训练时钟

`7 天 = 1 BOOK_SPRINT` 的本意是防止无限停留、强迫留出验证时间，不是要求“七天必须学完一套东西”。

如果研究开始围绕“今天该读到第几页”“轮到哪本书”运转，而不是围绕真实 unresolved question 运转，那么项目会重新退回外部课程表驱动。

校准：

`calendar cadence != learning trigger`

时间盒只触发复盘，不自动触发 COMPLETE、换书或理论升级。

### 2. 理论版本号也会制造虚假成长感

v0.1 -> v0.2 -> v0.3 的每次推进都有明确历史错误来源，但如果以后每次反省都升一个版本，版本号本身会变成“我在成长”的替代指标。

因此从现在起：

- 纯文字反省不触发理论版本升级；
- 新增一个 Gate 不自动触发理论版本升级；
- 新读一本书不自动触发理论版本升级；
- 至少要有新的独立 source conflict、implementation failure、negative-control result 或 clean prospective result，真正改变一个 operational claim，才考虑新版本。

当前继续停在 `反证情境压缩法 v0.3-alpha`，不为了显得进步而创建 v0.4。

### 3. “问题驱动”也可能被形式化成新的 checklist

如果每轮机械写 TOP 3 unresolved questions，但问题其实只是为了满足模板，仍然是被流程推着走。

真正的内驱要求：每个 research session 至少有一个主 Agent 自己当前确实无法回答、而且答案可能改变模型的真实问题。

收尾时至少给出一个：

`KEEP / REVISE / DELETE / NO-OP`

`NO-OP` 也是合法结论。不是每一轮都必须增加知识或规则。

## 二、从旧路继续抽象出的错误家族

过去反复出现的错误可以继续压成三个根：

### A. 奖励自己“看起来进步”

历史表现：100% 命中、实战能力百分比、真验证覆盖率。

现代变体：CI 全绿数量、Gate 数量、读完书数量、理论版本号。

共同问题：把过程指标包装成能力指标。

### B. 结果后扩大解释空间

历史表现：一次 miss 后增加全局优先级、换用神、换新闻解释。

现代变体：增加更多 context key、更多 branch、更多 method variant。

共同问题：复杂度增长速度超过真实区分力。

### C. 寻找支持而不是寻找攻击

历史表现：用成功案例证明书中断语。

现代变体：已经用某本书某几页支持一个实现修复，然后继续只读那些支持页。

共同问题：confirmation-by-selection。

因此下一本书必须先问：

> 哪些页面最可能证明我们当前实现或理论理解错了？

而不是：

> 哪些页面能证明刚才的修复是对的？

## 五、这轮决定

- `KEEP`：反证情境压缩法 v0.3-alpha 的六步骨架。
- `REVISE`：把 BOOK_SPRINT 理解为复盘节奏，而不是学习动力来源。
- `DELETE`：删除“每次深入反省都应该升级理论版本”的隐性冲动。
- `NO-OP`：暂不新增新的顶层 Gate / Registry 字段。

下一步不是再造 v0.4，而是让 Cycle 1 原页阅读与 full-rotation implementation test 去真正攻击 v0.3 和当前代码。
